# Changelog Settings

NASBot has no GitHub "changelog settings" panel to configure. Its changelog is a file
in the repository, and it is enforced by the release gate. This document describes the
settings that actually exist: where the file lives, what format it must have, and which
automated checks read it.

For the wider repository settings see [BRANCH_PROTECTION.md](BRANCH_PROTECTION.md) and
[GITHUB_RULESET_SETUP.md](GITHUB_RULESET_SETUP.md).

## 1. Location

| Setting | Value |
|:--------|:------|
| File | `docs/CHANGELOG.md` (single file, not `CHANGELOG/` per release) |
| Format | [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) |
| Section header | `## vX.Y.Z - YYYY-MM-DD` |
| Date meaning | the tag's creation date, from `git for-each-ref --sort=creatordate refs/tags` |
| Order | newest first; a work-in-progress `## Unreleased` section sits on top |
| Legacy path | `CHANGELOG.md` at the repository root is **blocked** by `scripts/quality_check.sh` |

Documentation moves, it does not duplicate: the runtime bundle ships
`README_RUNTIME.md`, never a copy of the changelog.

## 2. The Two Automated Checks

### `scripts/quality_check.sh` — the file must exist where it belongs

Runs as part of `ci_guard.sh` and as the local `pre-commit` hook.

- Fails if `docs/CHANGELOG.md` is missing.
- Fails if a legacy `CHANGELOG.md` (or `docs/CHANGELOG.md` from the pre-`docs/governance`
  layout) reappears in the wrong directory.

### `scripts/ci_guard.sh release <tag>` — the section must exist for the tag

This is the release gate, and it is stricter than it used to be. In `release` mode it
runs **two** checks that have nothing to do with each other:

```bash
scripts/ci_guard.sh release v1.6.2
```

| Check | Function | Refuses when |
|:------|:---------|:-------------|
| Semantic tag | `check_tag_semver` | the tag is empty, or does not match `^v[0-9]+\.[0-9]+\.[0-9]+([.-][0-9A-Za-z-]+)*$` |
| Changelog entry | `check_changelog_entry` | `docs/CHANGELOG.md` has no `## <tag>` header |

Both failures are hard exits, and neither depends on the other: a perfect
`## v1.6.2 - 2026-09-01` section does not save a tag named `1.6.2`, and a valid tag
does not publish without its section. Run the gate locally before tagging:

```bash
scripts/ci_guard.sh release v1.6.3
```

The header must match on the tag itself, so `## v1.6.3`, `## v1.6.3 - 2026-10-02` and
`## v1.6.3-rc1` all pass; `## Unreleased` and `## Version 1.6.3` do not.

The same function is a single `grep -E "^##[[:space:]]+${tag//./\\.}([[:space:]]|$|-)"`:
adding a line of prose under the header is enough, the content is not machine-checked.

### `.github/workflows/release.yml` — when the gate runs

```yaml
- name: Release guard
  env:
    RELEASE_TAG: ${{ steps.get_version.outputs.tag }}
  run: |
    chmod +x scripts/ci_guard.sh scripts/secret_scan.sh
    scripts/ci_guard.sh release "$RELEASE_TAG"
```

The gate is step 5 of the release job, before `build_release.sh`, before the checksums,
before the provenance attestation and before the GHCR image build. A missing changelog
section therefore fails the release **before** anything is published, and re-running the
workflow for the same tag fails the same way.

## 3. GitHub Release Notes

`softprops/action-gh-release` is configured with `generate_release_notes: true`, so the
body of the GitHub Release is generated by GitHub from the merged pull requests since
the previous release.

That generated body is **not** the changelog: it lists PR titles and never fails a build.
The file `docs/CHANGELOG.md` remains the authoritative, curated, human-written history.

There is no `.github/release.yml` in this repository, so GitHub uses its default
categories and labels. Adding that file (e.g. mapping `feat` → *Features*, `fix` →
*Bug fixes*, `docs` → *Documentation*, and excluding `chore`/`ci`) changes the generated
body only. Because the file is version-controlled, changing it is a pull request.

## 4. Writing an Entry

```markdown
## v1.6.3 - 2026-10-02

### Added
- **Something new**, with the file or command that provides it.

### Changed
- **A behaviour that changed**, and what the user has to do about it.

### Fixed
- The bug, and the symptom the user saw.

### Validation
- What was executed to check the release (gate, tests, a real deployment).
```

Rules that the tooling or the next reader depends on:

- One `##` header per tag, exactly matching the tag string.
- Never renumber or re-date a released section: the tag dates are the reference.
- `/config.json` is the bot's own configuration and has nothing to do with the
  `config.json` of this repository. Do not add one.
- Screenshot-free, no secrets, no real host names or user IDs in examples.

## 5. Tags Without a Section

`v0.2.0` through `v1.4.0` have no section in `docs/CHANGELOG.md`; those releases
predate the format. This is stated at the top of the file so a reader does not conclude
the changelog was truncated by mistake.

`check_changelog_entry` only looks for the tag being released, so those old tags can
still be rebuilt (`workflow_dispatch` with the tag input) without their sections.
Reconstructing them from the git history is optional maintenance work, not a gate.
